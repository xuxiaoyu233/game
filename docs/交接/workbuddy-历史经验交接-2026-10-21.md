## 3. 项目规划与研究经验（跨项目）

### P1 主体倒置：把用户原话拆成「核心选择/自动循环/结果展示」再排期

- **情境**：2026-10-20 用户验收 CodeBuddy V2 样板（完整院落 11 槽 + 选地建设 + 两类真实样板）。技术路径可运行、本地检查通过，用户仍否定方向。
- **问题**：用户原意是「放置成长后，场景自己逐步生成完善」；规划侧将其展开为完整院落、选地建设、设施晋升与随机组合主线——**主次倒置**，把结果展示做成了第二套经营流程；同时贴图与背景不匹配。
- **用户纠正（原话）**：「主体就是梅尔放置，然后我们的主页面不是我们主观去点击放置建造的，而是类似于放置后他自己生成的，我们是逐步完善的。」（来源：[候选输入](交接/候选输入/20261020-玩法主体与自动场景.json)，2026-10-20 会话）
- **原因分析（推断，有 PLAN 佐证）**：① 底座（CivIdle）具备建城机制，就被沿袭为产品方向——PLAN 明文「不因 CivIdle 底座已有建城机制而沿用其产品方向」；② 把「场景逐步完善」误解为「玩家手动建造流」；③ 技术验收通过掩盖了主体错误。
- **采用做法**：PLAN 重写为五步唯一活动顺序（方向收拢→放置主循环样板→自动场景样板→样板确认后逐步完善→后续可选成长），每步带退出条件；旧交接/规格/UI 稿统一标「已失去执行性」保留来源；明确「场景点击至多查看进度或跳转同一技能入口，不成为另一套经营主线」。
- **实际结果**：放置主循环样板已由 CodeBuddy 交付（42 项合同、两尺寸、300 秒真实离线通过，见[样板交付](证据/发展沙盘/放置主循环-20261020/样板交付.md)）；新方向真人试玩与审美确认**未做**。
- **适用范围**：已有放置产品的视觉化与开源底座采用；用户明确以建造布局为核心时不适用。
- **反例**：自动呈现成长 ≠ 自动替用户扣费施工，也不要求运行时生成图片；用户明确要建城时不应隐藏其主要选择。
- **保留状态**：现行产品合同；候选输入已在本地保存，**未 capture 进 skills 库**（见 §7.3）。

### P2 长期进度与「爽感」分开判断，不用类型标签替代产品约束

- **情境**：2026-10-20 用户认为当前框架过大、希望休闲肉鸽爽感；助手提议短局/副本，被撤回。
- **用户纠正（原话）**：「我们不要短局经验，要长期的，现在不要副本了，就是一个发展为主。」（来源：[候选输入](交接/候选输入/20261020-长期发展与肉鸽爽感.json)）
- **采用做法**：在已确定的长期结构内比较可行组合（有限发展选择、设施联动、真实成长反馈），不引入短局重置；先区分随机选择、组合联动、收益跃迁与短局/副本/清图。
- **实际结果**：仅完成长期组合规格与交接；**组合乐趣未实现、未试玩**（该规格后因 P1 纠正失去执行性，但「长期结构内找爽感」的方法仍有效）。
- **反例**：用户明确要短局/赛季/副本时按其要求比较；长期建设不自动优于短局。
- **保留状态**：现行约束；候选输入未 capture。

### P3 唯一计划 + 撤回项显式化 + 三类文档效力

- **问题**：多轮规划后存在 V2 交接、ui-v3、组合规格、C2 清单等多份可执行材料，相互冲突；执行者可能照旧材料干活。
- **采用做法**：① PLAN 唯一活动顺序 + 「撤回当前执行性」表；② `docs/README.md` 三类文档效力表（当前合同/交付证据/已撤回历史）+ 「撤回项的共同原因」集中记一处，不在每个文件各写一份；③ 交接 README 标「已失去执行性」。
- **实际结果**：2026-10-20 后无第二份执行计划；历史材料保留来源可追溯。
- **归属**：已被 skills 覆盖候选覆盖（SSOT：E-ebe715b05d9f covered；项目计划 SSOT：E-ffbfbdf30b2b candidate；README 可查找性：E-6a1b7a6c2747 candidate）；game 的「三类效力表」是可补 evidence 的具体实例。

### P4 「反复规划未推进」核查：规划何时有价值、何时变成膨胀

- **核查结果（事实）**：2026-10-18 一天内产出三份大规格（产品功能与科技目录 14 项功能/六分支/六时代/36 节点、扩展规格、首版规格），PLAN 交接基线当天三条均为「只修改规划/交接，未实现新玩法」；2026-10-20 用户纠正直接终止了规划扩张循环（当轮「未实施新玩法、未外部发任务」）。
- **区分（推断，有结果佐证）**：**以「冻结采用合同」结尾的规划产生了实际收益**——首版规格、C1 采用值、D1-C 采用合同都被 CodeBuddy 成功执行并本地验证；**以「扩大范围」结尾的规划变成膨胀**——V2/组合规格/ui-v3 沿底座机制扩张，被用户撤回。
- **改进做法（现行）**：① 每步带「验收/退出条件」与显式「待实施」状态，禁止把计划写成已发生；② 调研文档头部标 superseded、结尾写「本轮只完成研究……没有修复/实现/发布」；③ 方向收拢本身作为第 1 步，只改计划不编码；④ 交接提示词固定「交付后停止，不自动进入下一批」。
- **适用范围**：多阶段、多执行方的项目；不适用于用户明确要求先出完整方案再评审的场景。
- **反例**：规则/迁移/存档兼容的前置设计不能省——D0-R 数据保护、C1 迁移合同都是先设计后执行且必要。

### P5 研究必须落在「采用结论」，且与「已实现」分离

- **问题**：大报告若缺清晰采纳决定，会被误读为进度（如「素材已备」被当成「游戏已实现」；「资料整理」被当成 V1 已落实）。
- **采用做法**：每份调研以结论/采用表开头；来源逐一记「实际核对范围+固定 commit+许可」；明确「没有运行/没有修复/没有发布」清单；证据索引维护「未测项汇总」。
- **代表来源**：[网页画质与点击体验调研](规划/网页画质与点击体验调研-20261019.md)（结尾明写「没有修复 F1–F5、导出高清替换图、生成手绘资产、安装依赖或更新 Sites」）；[基础底座调研](规划/基础底座调研.md)（头部标注被 10-17 用户决定取代）。
- **归属**：报告组织法已被正式 skill `report-writing` 覆盖；「superseded 头注 + 边界句 + 未测项索引」可补 `source-backed-knowledge-management` / `project-planning` 候选证据。

### P6 先纯函数推演、后交 UI：口径问题在规则层定位

- **情境**：C1-R 前核查发现 UI 宣传与函数行为不一致（累计/本级 XP 混用「30/55」、固定「+8XP」不反映 1200 截断、协助固定「附 1 经验」）。
- **采用做法**：先读规则源码 + 纯函数推演（四技能到 Lv10 时长表）+ 9 组边界断言，把问题分级 P1/P2 写成「需交付的改进」表，再交 UI 收口；**不新增仓库测试套件**（符合 P4/测试简化政策）。

## 4. 游戏玩法与故事内容专属经验（留在 game，不升级为通用方法）

> 本节内容适用于本项目的机制与世界观语境；迁出项目会丢失适用条件，按用户要求**不**上升为通用 Skill。

### 4.1 玩法研究（game 专用）

- **G1 放置主循环三要素**：玩家核心选择 = 技能/作业；自动循环 = 产物/XP/解锁；结果展示 = 场景随真实进度完善。视觉变化必须由真实成长事实驱动，「自动生成」指成长结果的自动呈现，不发资源、不解锁规则、不自行推进等级。（PLAN 2026-10-20）
- **G2 底座机制 ≠ 产品方向**：CivIdle 的建城/科技/工人机制可复用其**实现**（Grid、生产、运输、存档屏障），不沿用其**产品形态**；关闭机制要追踪依赖（劳动力不是可忽略字段），不能只隐藏 UI。教训来源：P1 + [底座对照](规划/发展型沙盘玩法与底座对照.md)。
- **G3 舒适经营优先、生存后期可选**：普通模式无随机致死灾害/瘟疫/离线死亡；食水短缺保留增长/效率影响；挑战模式需明确风险、独立难度标识、可恢复策略，不默认追扣普通档历史时间。（PLAN「2026-10-20 最新取舍」）
- **G4 画质是分层诊断，不是分辨率开关**：构图/可见性 → 画布密度 → 纹理细节 → 渲染比例 → 素材风格 → 成长表现；不把提 DPR、放大小 PNG 当高清；同场景小样（农田/木工坊 1→2 星）先验证再推广；素材尺寸由显示预算（CSS px × 目标 DPR）反推。（[画质调研](规划/网页画质与点击体验调研-20261019.md)）
- **G5 PC/桌面浏览器交互特点**：轻 hover、点击选中单一主动作、拖动不误触、主要目标 44px、键盘可达、`prefers-reduced-motion`、保存失败持续可见并指明重试路径；桌面尺寸 960×720 与 1440×900 为主，手机/触屏/短屏已移出本轮。（[适配规格](设计/网页适配与视觉体验规格.md)、V1 复核与补修）
- **G6 经济路线比较的证据边界**（已有候选 E-ffe031e3fef5，本地库）：先冻结比较目标、初始状态、终态库存要求；算术复核、可达性测试、最优性搜索、真人试玩分别标明，不互相代替。来源：2026-10-11 路线算术复核 + `docs/内容资料库/资源与生产链.md`。

### 4.2 故事、内容与审美（game 专用 + 可迁移的组织方法）

- **S1 故事不阻塞工程，归档要可追溯**：0.8 故事玩法终止后，旧故事资料归档并留哈希/只读记录（`docs/历史资料/`、`docs/证据/历史/技能原型阶段记录-20261017.md`），当前「工程用通用功能词，不等待故事完成」。世界观/角色/故事线如重启，从归档与 git 历史进入，不凭记忆重写。
