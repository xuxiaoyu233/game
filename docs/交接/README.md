## 任务分工

| 任务                                                  | 执行者              | 目的                                                     | 交付                                      |
| ----------------------------------------------------- | ------------------- | -------------------------------------------------------- | ----------------------------------------- |
| [工程执行](GPT-工程执行提示词.md)                     | 网页版 GPT          | 在现有工程中完成单活动放置原型的实现和验收               | 可审查的源码/文档改动、检查结果与未完成项 |
| [新故事和命名研究](WorkBuddy-故事与命名调研提示词.md) | WorkBuddy           | 公开来源调研放置游戏并从头设计可串联的新故事             | 可脱离游戏仓库阅读的故事文献库候选包      |
| 复核和选择                                            | Codex，再由用户选定 | 查来源、因果、人物关系、命名、完整性、游戏循环适配与边界 | 修改后的候选包；用户批准后才进入下一阶段  |

工程原型不等待 WorkBuddy，使用通用功能名。WorkBuddy 不动工程源码和唯一 `PLAN.md`。二者没有共享可变文件，也不互相导入资料；完成后的故事候选再由 Codex 建立包外接入映射。

## 解耦与数据流

```text
公开资料 ─→ 来源和阅读记录 ─→ 作者研究解释 ─→ 虚构世界/人物/事件/关系
                                             │ Codex 审核、用户批准
                                             ▼
                                   工程维护的接入映射
                           故事编辑 ID → content ID / themes 文案 ID
                           + 获得条件、玩家可见范围、批准依据
                                             │ 显式类型与版本检查
                                             ▼
                                    domain 的有限规则
```

故事文献包要有自己的 README、稳定编辑 ID、版本、来源台账、命名表、世界/人物设定、故事节拍与关系索引。包内用相对链接，单独复制到别处仍可阅读。来源事实、WorkBuddy 的研究解释、候选创作和用户批准的设定应明确分开。编辑 ID 只供文档追溯，绝不是存档 ID。

故事包不收录游戏代码路径、TypeScript 类型、运行时实现、存档 schema、生产周期/XP/价格等生效机械数值或活动执行状态。工程接入表不复制整个故事包；它仅映射经批准且要进入游戏的条目、获得条件、文案和可见性。运行时不解析 Markdown，也不能靠角色名、中文别名或隐藏真相推测故事结果。

类目、资源名称、来源/生产/用途、技能和科技候选可以在各自资料库充分分析。科技/资源的世界内解释属于故事包；实际成本、解锁、产出、效果仅属于类型化工程定义。资料库中提出科技树不等于首版实现科技系统。
