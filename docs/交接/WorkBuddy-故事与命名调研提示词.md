## 研究游戏及证据要求

公开调研以下四款放置游戏：**Melvor Idle、Rusty’s Retirement、A Dark Room、Kittens Game**。在可用浏览器中查阅游戏官方介绍/商店页、作者或官方 wiki 等可靠公开资料；按所能实际读取的范围，比较这些与新项目有关的维度：

1. 初始行为与持续循环，玩家每次主动操作的必要性和低频回访方式；
2. 活动/技能/资源/生产链如何互相连接，何时出现新选项；
3. 目标、升级、科技或自动化如何提供有意义的选择；
4. 故事、世界揭示或事件如何挂靠玩法进程；
5. 小窗口/低注意力适配和容易造成负担的部分。

每个事实标明具体来源链接、页面/栏目、查看日期和真正读过的部分；区分官方宣称、游戏机制观察与自己的解释。查不到的项目留空说明，不拿搜索摘要冒充读过完整页面。采用游戏机制作抽象参考，**不复制名称、剧情、专有名词、文本、角色、世界观或素材**。不要声称这一小组样本代表全部放置游戏。

## 先比较，再完整展开

先提出 **3 个有实质区别的新世界/故事方向**。不要先预选原有救援/跨界组织套路。每个用同一张简表说明：候选新游戏名、世界一句话、玩家长期角色、第一件反复做的日常事情、生活资源与成长为何有故事意义、长期主问题、可能缺点、与 4 款参照机制的抽象联系。

用不超过 6 个维度的打分/理由表比较清楚度、延展性、放置循环融合、小窗口可读性、辨识度和工作量。可以推荐一个深入完成，但将推荐标为“待 Codex 复核、用户未选定”。三案均应可开发且能由同一轻量放置循环承载，不要靠末尾突然引入战斗、大队伍经营、异世界救援局或另一套货币才能成立。

对优选方案，完整写出：

- 2–4 个游戏/系列/第一卷名备选，给发音、含义、氛围、歧义和重名/既有作品碰撞的初步检查。命名建议是原创候选，检索范围与未检索的商标/法律状态都要如实注明。
- 世界的日常规则、空间/社会结构、短期压力、资源从哪里来/如何转化/为何有用，及与玩家长期生活直接有关的核心未知。范围小而可信，避免只靠大词和无限宇宙。
- 玩家角色：玩家能做什么、为何每天能重复一小段工作、为什么能在不频繁点击时持续成长、遇到目标时如何作选择。不要预设失忆、天选之子或未经铺垫的隐藏身份。
- 4–6 名有不同目的的人物角色卡。每人写稳定编辑 ID、身份/日常职能、眼前目标、长期欲望、能采取的手段、边界/误解/代价、起始认知、会改变的事实、出现在哪些节拍。避免角色只负责派任务、讲设定或替玩家做决定。
- 第一卷/第一大段的完整因果弧：开场疑问、实际任务、玩家第一次可验证发现、中段关系/资源/知识选择、看似解释、反证、人物行动造成后果、卷内可兑现的阶段答案、依然合理未解并推动下一段的问题。解释每一步为什么自然接上前一步；隐藏真相要有可追溯铺垫，不能事后推翻证据或用巧合连接全部人物。
- **6–10 个有序故事节拍**。每拍写触发前提、玩家正在做的日常活动/当前目的、角色所知与误解、得到的观察/证据、选择或行动、即时后果、延后影响、能解答/新生的问题、获得条件和可重看内容。列出漏过或重复进入的安全语义；不让随机事件决定唯一主线事实。
- 首个短任务不超过玩家一眼能理解的目标：它怎样自然使用通用材料/一项制作/当前活动，不强迫玩家为了读小说停产，也不冒领未经任务条件支持的永久结论。给一则适配小窗的任务摘要样稿，和一条回访结果样稿。
- 若世界内有科技/知识发展，另给**故事侧知识体系资料卡**：技术/知识条目的 ID、世界内问题、已有观测/来源、依赖哪些已验证知识、人物争议、改变了什么日常做法、尚不能解释什么。标明“编辑资料，不是游戏科技树/成本/效果定义”。自然科学事实、虚构推断和作者设定分列；不把科学词汇充作真实证据。

## 必须明确呈现的关系与因果

关系不能只有“他们是伙伴/敌人”的人物简介。交付可筛选的有向关系列表。每条至少包含：关系 ID、源 ID、目标 ID、类型、谁知道/相信什么、成立依据、起始状态和不对称处、触发变化的节拍/行动、之后的状态、玩家能观察到的后果、是否暂时/未证实、来源或创作依据。

至少覆盖：人物 ↔ 人物；人物 ↔ 群体/地点；世界规则 → 资源来源与日常活动；资源加工/用途 → 选择与代价；证据 → 问题/推断/阶段答案；关键行动 → 人际/社会/未来委托后果；伏笔 → 后续兑现。若关系是推断或角色偏见，要注明是谁的观点；一方不知情时不得写成双方对称事实。

另给一张“主线因果表”逐边列出前置事件、推理依据和影响；一张“问题—证据—回答—未解部分”表；一张“人物在第一卷各阶段变化表”；资源链画成来源 → 加工 → 用途 → 玩家目标，并指出哪些是故事解释、哪些可作为候选机械映射。为资源和类目给玩家易懂的功能名称，可另给一致的世界内叫法；说明名称是展示选择、工程 ID 仍待工程侧确定。每种拟进入核心循环的物品都有来源和真实用途，虚构的资源历史不能替代生产规则。任何线索不能无因出现，任何重要角色不能无因知道，阶段答案应被此前证据支持。

## 独立文献库交付格式

请把产物整理成一个独立目录 `story-library/`，可单独复制、压缩或搬迁。用 Markdown 和目录内相对链接，保证脱离游戏仓库也能阅读。建议至少提供：

- `README.md`：候选版本、研究/创作边界、导航、当前未获用户批准；
- `sources.md`：来源台账、访问日期、实际阅读范围、可靠性/局限、支持了哪些研究判断；
- `reference-games.md`：四款游戏的来源依据、机制观察、启发与明确不复制项；
- `names-and-glossary.md`：名字候选、统一词汇、歧义和名字碰撞查询边界；
- `classes-and-resources.md`：资料类目与玩家可见类别名称；核心资源的通用功能名/世界内别名候选、来源、转化、用途和故事关联；技能、活动、物品、工具、任务、科技等概念的分类边界。候选需易懂且彼此不混淆，不为世界观牺牲功能辨识度；
- `world.md`、`characters.md`、`story-arc.md`：优选候选的设定卡、关系和节拍；
- `causal-index.md`：关系边、主线证据链、问题/回答、资源与成长因果；
- `knowledge-library.md`：如适用，故事侧科技/知识资料卡及证据状态；
- `completeness-and-gaps.md`：检查矩阵、矛盾、待研究项、合理保留的未知。

所有 ID 只在这个故事库中使用、英文 kebab-case、稳定且不复用；按 subject 使用清晰前缀，例如 `person-*`、`world-*`、`beat-*`、`question-*`、`evidence-*`、`relation-*`。它们不是游戏机械 ID、文案 ID 或存档字段。不要在包里写 `src/...` 路径、TypeScript 名称、runtime 实现、存档 schema、XP/秒、价格/配方/升级效果等工程事实。

不论能否写磁盘，都要在最终答复提供完整包：能写文件时列出相对路径；不能写时按路径逐个给出完整 Markdown 内容。只需独立的**故事内容包**，工程侧命名、机械数值、活动和存档接入由其他任务负责，切勿修改工程或正式故事文档。
