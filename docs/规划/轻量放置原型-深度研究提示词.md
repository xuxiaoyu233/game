# 轻量放置原型：网页版 ChatGPT 深度研究提示词

整理日期：2026-10-11。用途是研究和产品对齐，不是已批准的实施计划；唯一执行计划仍为根目录 `PLAN.md`。本文件不改变现有游戏规则或故事正史。

以下正文可完整复制到网页版 ChatGPT。若上传 `PLAN.md` 或旧合同，请提醒研究者：它们记录现状和历史决定，其中过度复用旧玩法的部分正在重新评审，不应直接当成新版约束。正文已包含必要背景，不上传附件也可开展研究。

---

我正在做一款本地优先的 Windows 桌面放置游戏，暂名《诸界救援局》。我想先做一个接近 Melvor Idle 基础体验的轻量原型，暂缓宏大的救援副本、多人管理和无限流内容。请实际搜索、比较和推演，帮助我重新理解产品方向，形成可以交给开发者细化的研究报告。当前只做研究和设计，不写实现代码。

## 1. 我的目标与边界

- 游戏可以放在电脑角落，安排活动后收起，回来理解所得、停机原因和下一步。
- 初期不需要管理多个角色或人员岗位。优先研究单角色、一个主活动的模型；请解释它的机会成本与适用边界，不把“所有系统永远不能并行”当成不可修改的规则。
- 核心候选循环是：选择活动 → 持续获得资源和经验 → 制作有用物品 → 升级工具或解锁新活动 → 重新安排活动。
- 先做小规模但完整的玩法，不复制 Melvor 成品的全部技能、物品和成长系统。建议以两项核心技能、一条完整生产链作为起步预算；如果这个预算不合理，请说明原因并提出最小调整。
- 希望保留扩展空间，但不能为了未来先搭建大量空系统。故事、战斗、副本和新世界需要等基础循环有说服力后再接入。
- 小窗设计目标为 420×600，360×480 为收缩压力场景。首屏需要能理解当前活动并执行该页面的主操作，允许有目的地浏览长列表。
- 不以连续手动点击作为基本生产前提，不用单纯涨价或延长等待冒充深度。
- 暂不考虑多人交易、账号、云同步、手机接续、自动生成世界、运行时 AI 对话、复杂地图建造、随机装备词条和正式美术音效。
- 开发以小规模、AI 协助为背景；实际人员和工期尚未固定，不要假设存在完整开发团队或承诺具体上线日期。

## 2. 当前状态与已知问题

以下是本地源码和隔离新档页面检查所得，不是玩家调研或留存数据：

1. 当前基线为产品 0.8.0、内容 14.0.0、存档 schema 9；旧版 0.7.1 数据继续隔离。
2. 已有长期库存、三种岗位自动生产、单配方队列、专业经验、离线补算和保存恢复。驻地岗位默认三人并行执行，副本另有独立四人配置。这些是旧实现事实，不是新版必须保留的产品要求。
3. 主空间采用“出发 / 成长 / 档案”，新档默认展示故事和出发准备。“成长”同时堆放回访摘要、库存、专业经验、设施、岗位、配方、永久兑换和研究。
4. 420×600 下，“成长”页约 2700 像素高，第一组制作按钮位于页面约 1306 像素处；360×480 下页面约 2877 像素高。开启“简洁”仅减少约 46 像素。导航已有吸顶，但没有解决内容职责混杂。
5. 新档回访摘要会把极小增量显示成多项“+0”，占据首屏空间；这说明反馈显著性还未打磨。
6. 当前原料为回收合金、蓄能芯、生物纤维。单人每小时分别产出 6、8、4 单位。回收蓄能芯获得工程经验，工程制作又占用该岗位人员，技能职责不直观。
7. 当前工程等级 2 阈值为 8 XP，单人工程回收每小时 6 XP，因此只靠该作业需 80 分钟。制作每批获得 2 XP，所以这不是所有路线的必经等待。结构板制作每批 3 分钟；屏障组件每批 4 分钟。这些数值只供诊断，不应直接继承。
8. 结构板可扩建仓储；屏障组件用于副本界锚加固。医疗包可制作但未接消费端，界锚框架依赖尚未接入来源的稀有材料。采集等级缺少对应的新作业解锁。
9. 已有测试证明了部分规则与流程，但部分小窗用例先滚动到按钮再检查横向不溢出，没有证明主操作容易发现。没有可靠的长期试玩、回访或留存结论。
10. 旧计划曾明确“复用岗位并行生产、不要求一次只运行一个活动”。我们正在重新评审这个决定。请不要为了维护旧方案而解释问题。

我的直觉是：我们过度复用旧玩法，以功能接通代替产品体验闭合。但这仍需分析，请检验这个判断，也指出有价值的现有部分。不要把所有问题笼统归为 UI，也不要直接宣布所有源码都应推倒重写。

## 3. 研究方法与证据

- 以 Melvor Idle 为主要参照，另外挑选 2–3 款确实能补充设计视角的游戏。可从 Idle Clans、Kittens Game、A Dark Room、Rusty’s Retirement 等选择，也可以选择更合适的对象并解释原因。
- 不做泛泛的热门游戏清单。分别研究它们的一个具体循环、成长解锁方式、库存用途、活动选择和回访体验。
- 优先使用开发者网站、开发日志、官方商店、官方或社区维护 Wiki、可核实的开源源码。社区维护资料需要标注性质。
- 论坛评论只用于发现常见困惑、失败体验和可验证的假设，不把几条评论当成普遍玩家结论。
- 记录适用版本或资料时间。不能读取页面、只有搜索摘要、不能核实当前版本时要说明；不要把历史机制当成确定的现状。
- 关键结论提供直接支持它的链接。不要用商店宣传证明一个机制改善了留存，也不要声称自己实际试玩了没有运行的游戏。
- 区分“来源明确的机制”“设计推断”“本项目候选方案”“需要试玩验证的假设”。允许指出不存在足够证据的所谓最佳实践。

## 4. 需要回答的设计问题

### A. 我们到底与 Melvor 的基础体验差在哪里？

分析玩家第一次打开、启动第一项活动、获得第一份产物、第一次制作、第一次升级、第一次离开再回来这条旅程。

针对每个差距写清：当前表现 → 玩家需要理解或操作什么 → 为什么产生负担或缺少乐趣 → 推荐修正 → 如何验证。分别判断问题属于核心循环、技能成长、经济关系、信息架构、操作反馈还是内容不足。

请明确：哪些现有能力值得保留，哪些旧玩法应该退出轻量原型，哪些结论仍有不确定性。

### B. 科技树是否必要？应该怎样与技能、工具和配方分工？

比较至少三种可行的成长结构：

1. 技能等级自动解锁作业和配方。
2. 技能等级加工具升级，暂不设置独立科技树。
3. 技能等级加一个小型分支科技树。

区分技能等级、逐物品熟练度、工具、配方解锁、研究、科技树分别解决什么问题；哪些可以合并，哪些初期根本不需要。

特别检查：

- 科技节点解锁新的行动，还是只增加倍率？
- 两条分支有没有真实资源或时间机会成本，还是最终全买且顺序几乎无区别？
- 是否需要不可逆选择？它给轻量放置增加的收益是否值得重置和理解成本？
- 研究是否占用主活动、消耗材料或只作为购买动作？三种方式的取舍是什么？
- 是否出现“需要先完成被该科技阻止的任务才能解锁该科技”的循环依赖？
- 完全不用科技树，能不能实现同样的早期成长体验？

如果推荐科技树，给出约 6–8 个节点的候选示例，逐项列出前置、成本、效果、新增选择、资源来源和消费端。预算是范围限制，不是强制凑满节点。如果不推荐，请给出完整的替代解锁路径。

### C. 少量玩法如何形成真实选择？

研究活动对象选择、材料用途竞争、技能解锁、配方制作、工具装备、仓库管理、目标任务与轻量挑战。对每项判断“首版需要 / 下一阶段 / 暂不需要”，说明它解决哪个已经存在的问题。

用一个最小生产链示例说明：同一资源怎样有两个用途；玩家为何选择先升级效率或先解锁能力；什么时候值得切换活动；怎样避免一种路线在所有目标下都占优。不要为制造差异强行加入多种货币、随机失败或复杂词条。

原型命名可以先使用木材、矿石、工具等容易理解的功能名，也可以保留回收和工程风格；请比较理解成本，不把示例命名写成已批准的新正史。

### D. 经济与节奏怎样闭合？

为推荐的最小原型给出一份候选经济表：每个活动的来源、周期、产物、经验；每个配方的输入、输出和用途；每个升级的成本与效果；必要的容量和停点规则。

至少推演两条路线，用明确假设、实际消耗和关键解锁说明其差异，检查初始生产可达、资源守恒、工具升级前后的差别和没有材料死锁。无法实际计算时只给公式和待校准项，不伪造模拟结果。

分别讨论初次几分钟、首次较长挂机、第二次回访及基础内容结束后的体验。时间仅用于观察节点，不设置固定等候才能继续故事；不要用“有几天可等待”证明“有几天内容”。

检查缺料、仓满、批数完成、切换活动、暂停、离线回来各自应发生什么。没有意义的少量变化不应生成一整页摘要；升级和解锁需要有清晰反馈。

### E. 分类与小窗界面怎样组织？

先定义每个页面的职责，再比较两种候选：

- 平铺“采集 / 制作 / 仓库 / 升级”。
- 技能导航与仓库、升级等工具入口分组。

不要直接搬完整 Melvor 侧栏到小窗，也不要只重命名现在的“成长”页。解释推荐方案如何在仅两项技能时保持简单、在后来增加技能时仍然可用。

给出 420×600 与 360×480 的文字线框，标出当前活动状态、技能等级、选中对象、投入产出、周期、下一解锁和主操作所在位置。说明哪些信息常驻、哪些进入详情、哪些只在适用状态出现。

区分浏览页面、选择对象和真正切换活动；浏览仓库不应意外中断活动。说明开始、暂停、恢复、切换与批数设置的按钮职责，以及材料不足或锁定时的原因和下一步。可滚动列表不必全部挤入一屏，但不能用缩小字体或默认折叠关键操作来完成小窗适配。

### F. 怎样保留后续故事与世界扩展能力？

只研究最小扩展边界：内容数据、展示主题、纯规则、库存、技能和当前活动。说明以后如何让一份新世界契约消费既有物品、提供一个新用途，而不新建一套互不相通的经济。

当前工程是 TypeScript + React + Tauri。时间由运行时注入，纯规则不访问时钟、随机数、DOM、网络或磁盘；UI 统一发命令；保持单一运行时、动作队列和保存队列。保存、离线、导入及失败恢复有既有屏障。

可靠基础设施优先复用，但这不要求复用旧多人玩法。不要先设计任意脚本执行器、通用任务图引擎、动态插件体系或生成器。如果新玩法改变权威存档语义，要说明显式迁移或独立新档的取舍，保护旧进度；没有源码附件时不确定具体接口，不编造已兼容的结论。

## 5. 报告交付与分阶段规划

请按以下顺序输出中文报告，正文控制在便于讨论的篇幅，详细数据可放附录：

1. **决策摘要：** 当前产品最关键的三处偏差；推荐的轻量定位；科技树是否进入首版；哪些旧系统退出首版。
2. **机制对比与差距表：** 来源、具体机制、为什么有用、适用条件、在我们这里怎样简化，以及反例或风险。
3. **推荐原型：** 两项左右核心技能、完整循环、候选经济表和两条路线推演。至少解释一个具体的玩家选择，而非罗列功能。
4. **成长结构：** 等级、工具、配方和科技树的分工；必要时给出小型依赖图，并检查循环依赖。
5. **页面与完整旅程：** 页面职责、两个尺寸线框、操作状态、首次进入到回访的具体体验。
6. **3–4 个阶段的交付计划：** 按依赖安排完整可试玩切片。每阶段写玩家新增能力、细粒度工作、涉及模块类别、进入条件、集中验收与停止扩张条件。不要把仓库、技能条等零件单独当成完整交付。
7. **取舍与待确认项：** 首版、后续和暂不做清单；需要我们决定的少量关键问题；能证伪推荐方案的试玩结果。

验收分开记录规则推演、自动测试、浏览器体验、Windows 原生交互与真人试玩，不能互相替代。只在完整阶段结束集中运行相关门禁；阶段内只做必要的定向检查。页面验收要检查首屏与操作路径，不能只检查自动滚动后的按钮宽度。

最后做一次必要性自检：删除任何无法对应玩家问题、无法说明新增选择、没有真实消费端，或当前规模不需要的系统。请独立判断并明确推荐，不要为了显得全面把所有参照游戏的玩法合并进我们的首版。你不能直接访问我的本地目录，也不要假设已读到未上传的源码。仅在缺失信息会实质改变研究方向时提出不超过三个问题，其余使用明确标注的假设继续。
