## 结论

两个缺口均按验收方向修复：

- P1：恢复开始前**等待已有保存队列收敛**，再补算；恢复期间新到的常规保存被挂起；`failed` 态下队列残留与新到任务都被拒绝。实测恢复期间磁盘快照不前进，队列交错场景下最终快照与内存一致，重载不再重复 144 tick。
- P2：首次引导模态**延后到首次提交成功之后**，提交失败路由前再 `hideModal()` 兜底。新档首次提交失败时错误页直接可见、无覆盖模态，**直接点击重试**（未由脚本移除模态）即可成功进入 ready。

## P1 已有保存队列绕过恢复屏障

**根因**：`saveGame()` 只在入队检查生命周期；`doSaveGame` 的 finally 无条件取下一项。恢复开始前已排队的常规任务会在补算批次之间序列化当前状态，`savedAt` 仍是补算前边界。

**修复**（`Global.tsx`、`logic/ClientUpdate.tsx`）：

1. 新增 `drainSaveQueue()` 与 drain waiters：队列清空时统一唤醒等待者（`notifyQueueDrained()` 在 `doSaveGame` 的 finally 调用）。已入队任务写入的是补算前的一致状态（快照与 `savedAt` 同源），因此先收敛是安全的。
2. 后台恢复入口改为：`beginRecovery()` → `drainSaveQueue()` → `runOfflineCatchUp()` → 推进内存边界 → `commitSnapshotDirect()` → `markGameReady()`。恢复期间新到的 `saveGame()` 因 `lifecycle !== "ready"` 挂起，不会重新入队。
3. `doSaveGame` 的 finally：若 `lifecycle === "failed"`，`splice` 掉队列中所有残留任务并全部 reject，不再自动启动下一项——残留任务不能绕过 failed 状态写盘。
4. 内部提交仍走同一队列（`commitSnapshotDirect`），不受生命周期检查阻塞，不会因挂起队列头死锁；调用方语义保持 resolve/reject。

## P2 首次提交失败页被欢迎模态遮挡

**根因**：`Bootstrap.tsx` 在首次提交之前 `showModal(<FirstTimePlayerModal />)`；提交失败只切换路由，旧全局模态仍在。

**修复**：

1. 首次欢迎/伟人选择模态从「提交前」移到「`markGameReady()` 之后」；离线摘要弹窗仍保持原优先级。
2. 提交失败分支在 `routeTo(SaveCommitFailedPage)` 之前 `hideModal()`，兜底清掉任何已存在的全局模态（含离线摘要）。

**验证**：
