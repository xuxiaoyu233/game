# 工程规范

本规范保留根目录桌面技能原型的工程合同；当前发展营地以网页版为主，适用下述新旧工程范围，不增加原生接入/构建工作。旧原型名字和主题可替换，技术标识、路径与存档协议变化须显式审查。阶段顺序见PLAN；本规范不维护阶段状态。

**2026-10-17 范围补充**：根 `src/**` 的命名、纯规则分层、GameRuntime、JSON 校验与旧视觉要求继续适用于技能原型。用户已授权的 `next/civ-idle/` 底座验证允许保留原生目录与内核，具体边界见[架构说明](架构说明.md)；不能套用旧目录门禁重写上游，亦不能关闭上游类型检查逃避错误。新增代码保持规则/数据/展示分离，来源许可和存档安全要求照常适用。新沙盘视觉按[首版规格](规划/发展沙盘首版规格.md)，下文“单一光晕”不限制新场景的多处设施灯光。阶段内不自动跑检查，阶段末只对实际工程和影响范围集中验证，纯规划不跑游戏测试。

## 命名与结构

| 对象                       | 规则                                    | 示例                             |
| -------------------------- | --------------------------------------- | -------------------------------- |
| 文件夹、普通 TS 文件       | 英文 kebab-case                         | `save-codec.ts`                  |
| React 组件文件、组件、类型 | PascalCase                              | `GamePanels.tsx`、`GameState`    |
| 函数、变量、属性、方法     | camelCase                               | `advanceTime`、`lastSimulatedAt` |
| 模块常量                   | UPPER_SNAKE_CASE                        | `BASE_GAME_DEFINITION`           |
| 机械内容 ID、主题 ID       | 英文 kebab-case，创建后保持稳定         | `extractor`、`supply-cache`      |
| 单元测试                   | 与被测文件同目录 `.test.ts`             | `engine.test.ts`                 |
| 浏览器验收                 | `tests/browser/*.spec.ts`               | `game.spec.ts`                   |
| Rust 源码/函数/变量        | Rust snake_case；结构体/枚举 PascalCase | `save_store.rs`                  |

UI 中文文本不作为 ID。存档保存 ID 和事实，不保存中文名称、图标、计算结果或主题。
文件命名和依赖边界由 `check:architecture` 自动检查；类型/变量命名、Promise、React hooks 由 ESLint 检查；格式由 Prettier 和 rustfmt 检查。

## 代码约束

- 使用 TypeScript strict、exactOptionalPropertyTypes、noUncheckedIndexedAccess；外部 JSON 从 unknown 开始验证。
- 游戏状态只读；规则纯函数产生新快照；时间由调用者注入。购买前先用旧产量结算。
- 余额和产量保留小数，显示层格式化；禁止为了显示将存档取整。超出安全数值范围显式拒绝，不写 Infinity/NaN。
- 同一动作的扣费、数量、解锁记录一起提交。失败不部分修改状态；时间结算独立保留。
- 外部副作用通过 ports；浏览器和桌面分别适配。浏览器不调用原生接口，规则不依赖平台。
- 类型正确不能替代数据验证。定义、主题、存档各有验证器；内容版本变更需设计迁移和补算边界。
- 错误必须可见、可恢复。保存失败保留内存进度和 dirty 状态；不清空用户存档。不使用空 catch 隐藏核心保存失败。
- 游戏核心、内容、主题、存档和运行时不引入外部业务库。扩大模块边界需同步更新规则与架构说明并说明理由。

## 视觉主题依据

主题的物理场景句（唯一依据，同步写于 `src/themes/eras.ts` 文件头注释）：「深夜熄灯的书桌前，只有屏幕亮着，一个人在挂机。」

这句话强制推出整套视觉方向：深色底（房间熄灯）、单一光晕（只有屏幕这一处光源）、低环境光（任何元素不得与正文争光）。任何改色、改背景、改字阶的提案都必须能对照这句推导；推导不出来的提案不成立。禁止「放置游戏=暖棕工坊」这类一阶反射，也禁止「不要 SaaS 奶白所以改成编辑排版风」这类二阶反射。

落地约定：时代演进（7 档调色板 + tone 语义色相 + 场景位图）全部由 `getEraId` 纯派生驱动，零存档状态；色彩用 OKLCH 描述并采用「承诺」策略（面板底色本身带时代色相，chroma 0.02–0.04；一个饱和强调色承载 30–60% 视觉表面）；对比度硬门槛由 `scripts/check-theme-contrast.mjs` 门禁（正文 ≥4.5:1、次要/强调/tone ≥3:1，对背景/面板/浮层逐一校验；门禁按 `src/themes/eras.ts` 的调色板键集动态取 7 套，新增时代自动纳入）。

## 依赖方向

`main.tsx` 是组装入口。`app` 只呈现运行时快照、主题和规则定义；`runtime` 调用 domain/persistence/platform ports；`persistence` 只验证规则数据；`platform` 实现副作用。规则层不向外反向依赖。测试可跨层组装完整合同，生产代码不能。

## 工作流

分层、目录、当前/目标保存位置以[架构说明](架构说明.md)为唯一合同。README 提供入口，PLAN 管唯一阶段进度，本规范不另维护路径表或任务状态。

1. 明确需求、原子行为和验收条件，优先复用既有接口。
2. 修改最小责任范围，新的机械内容和主题分别修改配置。
3. 按最新用户 AGENTS，日常开发运行 `check:quick` 做格式/类型/Lint，不跑测试；不在每个子任务后重复完整门禁、单测与 e2e。隔离底座使用对应工程检查路径。
4. 完整玩法阶段或 UI 改版阶段结束时集中跑一次适用门禁（见下）；涉及界面加一项浏览器启动冒烟；涉及 Windows 外壳才跑原生检查和构建。
5. 更新文档的真实实现状态和限制。保持单一计划，避免散落多份相互冲突的路线。

每项协作声明输入 HEAD/资料版本、可写文件、整合负责人和交付位置。同一工作树一次一个写入任务，独立 checkout/worktree 才能隔离工程改动；共享入口、保存合同、门禁、锁文件和根文档由一个负责人串行整合。跨层必需修改列入本阶段任务清单，不要求对常规可逆改动反复询问用户。

阶段内部只做定位当前问题需要的定向检查；阶段末集中跑适用门禁，不在每个子任务后重复整套。修复后复跑失败项及受影响范围。构建成功不能替代实机或真人体验。

推荐提交格式 `feat(domain): add ...`、`fix(runtime): ...`、`docs: ...`、`chore: ...`。小而完整的提交；锁文件随依赖提交。当前不配置强制 Git hook，标准命令和 CI 是检查入口。

## 函数封装与模块深度

- **单文件 ≤300 行**：超过即按职责拆文件，不为凑数拆文件。
- **组件只做渲染与事件转发**：React 组件文件（`PascalCase.tsx`）不含跨区块复用的计算；状态、队列、dispatch、存档屏障集中在 Shell 组件，经 props/回调下发。
- **派生逻辑单一出处**：同一计算（缺料清单、建议目标、仓库关系、格式化）只在一个非组件模块（`kebab-case.ts`）实现，其他文件 import 调用，不得各写一份。
- **helper 进非组件模块**：纯函数（格式化、建议、派生）放组件同目录的 `kebab-case.ts`，不在组件内定义跨组件可见 helper。
- **Shell 保留的职责**：运行时订阅、tick 效果、保存/隐藏屏障、偏好持久化、页签与锚点导航、错误码映射。
- **新模块放 `src/app/skill-prototype/`**：一个区块一个组件文件，props 用 `readonly` 接口显式声明；组件不直接 import content 或 docs。
- **展示层数值必须来自 domain**：周期时长、产出/小时、经验/小时、距下一级 ETA、离线收益一律调用 `src/domain/skill-loop/rates.ts`，UI 不得自行乘除工具/增益/全局倍率——两套公式分叉会给玩家错误预期（本项曾出现过忽略增益的漂移，已收敛）。

## 测试政策

**发展期以完成可玩的大阶段为目标，测试只覆盖关键合同**（以用户 2026-10-17 最新 AGENTS 替换此前默认不新增的表述）。新增规则必须带合同测试，存档 codec 与迁移保留必要验证；不把补单测、重复全套自证或测试数量增长当作产品推进，不为纯派生展示另设测试阶段。

- 单测：保留核心规则、运行时屏障、存档 codec/迁移等合同；仍不纳入 `check`，只在阶段末按影响范围运行。新增规则配必要合同测试，修复已有高风险缺口优先复用或补最小回归；不扩成逐建筑、逐 UI 或覆盖率用例。
- e2e：只保留 1 项启动冒烟（`tests/browser/game.spec.ts`：标题+首操作可见+无控制台错误+双窗口布局）。视觉与时代证据截图属于脚本产物，放在 `scripts/visual-evidence/`，用 `npx playwright test --config playwright.evidence.config.ts` 单独跑（结果输出到 `.cache/`，不进 e2e 门禁）；时代证据截图落在 git 跟踪的 `docs/证据/时代演进/`，便于 review 与复跑复现。
- 验收方式：在完整玩法或 UI 改版大阶段末，按 `PLAN.md` 一次检查启动、主要操作与布局；改动涉及保存或兼容性时才检查保存重载与对应迁移。只记录实际执行的范围。
- 阶段内修复只复查失败项及受影响路径，不从头重复全套。截图用于美术判断，不扩充为逐控件行为测试。

## 自动检查

| 命令                                                  | 覆盖                                                                                                                                                                                                                                            | 运行时机                 |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `npm run check:quick`                                 | 格式、TypeScript、ESLint                                                                                                                                                                                                                        | 定位问题时按需运行       |
| `npm run check`                                       | quick + `check:architecture`（文件命名/依赖边界）+ `check:content-docs`（内容资料库链接与实现路径）+ `check:content-json`（内容 JSON 结构与不变量）+ `check:content-keyset`（内容 ID 集合指纹）+ `check:theme-contrast`（7 套时代调色板对比度） | 阶段末一次               |
| `npm run test:e2e`（`./scripts/project.ps1 e2e`）     | 真实浏览器启动冒烟                                                                                                                                                                                                                              | 阶段末                   |
| `./scripts/project.ps1 native-check` / `native-build` | rustfmt、Clippy、Rust 测试与 Windows 构建                                                                                                                                                                                                       | 阶段末，影响 Rust/桌面时 |

CI 配置提供相同门禁，远程 CI 是否通过以实际运行记录为准。纯文档改动不跑浏览器/原生全套。

`check:content-keyset`（内容 ID 集合指纹，防「版本号相同但键集漂移」）与 `check:theme-contrast`（7 套时代调色板对比度）是最新加入的两项，均已进入 `check` 链。

**新增顶层区块必须加入内容层组**：场景层与极光层是 `position: fixed; z-index: 0`，而**静态常规流内容会画在它们下面**，只有 `position: relative` 或自带层叠上下文（如 `backdrop-filter`）的元素才能穿出来。2026-10 同类问题出现两次：技能列表与页签被场景图盖住（`e9cc465`）；树视图的目录与详情「布局正确、`elementsFromPoint` 命中、背景不透明，但像素不显示」（`43b2cea`）。因此 `.skill-prototype-header / -status-wrap / -tabs / -tab-panel / -tree` 共享 `position: relative; z-index: 1`；新增顶层区块时加进这个选择器组，不要另起一套层级。

**排版令牌纪律**：间距只用 4px 网格上的 `--space-*`（2/4/6/8/12/16）；行高只用 `--line-title/-heading/-body/-caption`，组件内不得再写 `line-height` 字面量；数字元素默认继承根节点的 `tabular-nums`。组件里出现新的魔法数字时，先判断它是否该成为令牌。

## 内容添加流程（JSON 平台）

内容以数据表达，机制代码不改：

1. 改 `src/content/data/` 对应域文件（skills/items/activities/recipes/tools/tool-upgrades/profile）；新增物品/技能/工具只动各自文件，初始记录由加载器派生。
2. 同批补 `src/themes/skill-prototype-v1.ts` 文案（技能/物品/类目/活动/配方），否则启动主题校验失败。
3. 该内容阶段结束时统一跑 `check`（含内容 JSON 的结构、引用与不变量）；阶段内仅在定位相关问题时单跑 `check:content-json` 或 `check:quick`。
4. bump `profile.json` 的 `contentVersion`，并在 `src/persistence/skill-prototype-save-migrations.ts` 加对应加法迁移分支（同 schema 内容增量保留回执与增益，只零值初始化新键）；同时登记冻结定义表（p1–p4 模式）。
5. **ID 集合变了就必须 bump 版本，并且必须在 `src/content/keyset-manifest.json` 新增条目**：`check:content-keyset` 比对 items/skills/tools 的 ID 集合指纹，同一版本号下改动 ID 集合即失败（重新生成清单：`node scripts/check-content-keyset.mjs --print`）。**版本号只表示「这份存档自称属于哪个内容版本」，不等于记录键集完整**——2026-10-16 的死档就是「版本号相同但键集漂移」（先改版本号、后改 ID 集合）造成的：存档既走不了同版本快路径，也没有对应迁移分支，游戏直接无法启动。确需沿用同一版本号时，显式更新清单并在提交信息里说明理由。
6. 同步内容资料库台账与 `PLAN.md` 的阶段/验收记录。
7. **仅根技能原型：改动影响节奏的内容（曲线、活动周期/产出、工具倍率、增益）必须跑节奏审计**：`node scripts/audit-pacing.mjs` 按根内容推算各技能到满级的时长分布与曲线尾部占比，确认落在 `--max-total-hours`（总时长上限）与 `--max-tail-share`（尾部占比上限）门禁内；曲线尾部被重定时工具会输出前后对比，须随提交说明一并给出（旧曲线资料见[历史生产链](历史资料/技能原型内容库-20261016/资源与生产链.md)，实际值仍以根内容代码为准）。该工具属于content10.0.0原型，不套用于next/civ-idle；当前营地沿自身采用合同与阶段检查路径。

规则若要扩展（新效果、新命令），先改 `docs/规划/轻量放置核心合同.md`，再实现 domain、校验与 codec，最后补迁移。

## 内容资料与运行时代码的边界

当前营地的命名、生产、成长、建筑、文案、素材与扩展统一从[内容资料库](内容资料库/README.md)查阅；[玩家语言规则](内容资料库/界面语言与信息层级.md)只维护一份正文。编辑资料、生效机械定义和展示映射各有责任源；文档不直接驱动运行时，资料中的版本数值不作第二配置。当前规则看首版/C1/D1-C采用合同与next工程实际定义，旧[轻量放置合同](规划/轻量放置核心合同.md)仅约束根技能原型。科技候选不等于已进入游戏，新行为仍须规则与兼容审查，唯一实施顺序在根PLAN。

Markdown 记录创作事实、证据、来源和候选关系，不是运行时输入。游戏行为以 `src/domain`、`src/content`、`src/themes` 和 `src/persistence` 为准；文档中的 ID 只有被代码消费并完成兼容性审查后才成为机械内容。历史 ID 不自动沿用到当前产品。新增或变更内容资料时，应更新责任文档和交叉索引；若要进入游戏，还需同步更新代码映射、内容版本/存档迁移评估及 `PLAN.md` 验收记录。

资料改动至少运行 `npm run check:content-docs`；它检查 `docs/内容资料库/` 与 `docs/规划/` 的本地 Markdown 链接和其中声明的 `src/`、`scripts/`、`tests/` 实现路径存在性。完整工程变更按本规范运行项目 `check`；内容资料检查通过不代表内容已进入游戏或通过玩家试玩。
