# 机器可读内容与游戏资料库桥接方案

更新：2026-10-07。状态：F-01 已完成首个 TypeScript 故事档案投影与引用校验；没有建立通用叙事图、Markdown 转换器或 LLM 接口。

## 结论

资料库需要同时服务作者、游戏和未来的 LLM，但不应要求三者直接读写同一份自由文本。建议维护三种职责明确的内容：

1. **资料库记录**：Markdown 保存完整背景、来源、争议、作者真相、待回答问题和交叉关系，供作者研究与审阅。
2. **游戏内容**：`src/content` 保存规则事实与稳定 ID，`src/themes` 保存玩家可见的标题、描述和对话。游戏只装载代码导入的内容定义，不会自动解析 `docs/` 下的 Markdown。
3. **运行时叙事投影**：未来如需事件组合或 LLM，只传递经筛选的、带类型的少量事实 ID、可见性和白名单引用；不把整套设定集、隐藏作者真相或完整存档送入模型。

资料库负责丰富与可追溯；代码负责当前游戏实际生效的规则；主题负责屏幕上展示的文字。投影层以稳定 ID 引用前两层，**不复制机械条件，也不让模型修改权威内容**。

## 当前代码读取路径（源码核对）

- `src/main.tsx` 导入 `EXPEDITION_DEFINITION`、旧内容版本和 `GAME_THEMES`，验证主题后创建远征运行时。
- `src/content/story.ts` 定义线索如何获得、所需项目、对话前置条件与选项效果；它引用 `src/domain/expedition/types.ts` 中的类型。
- `src/content/expedition.ts` 定义世界、任务目标、事件、事件选项与派遣项目等机械内容。
- `src/themes/story-copy.ts` 定义章节、线索、对话的玩家可见文案；界面 `src/app/StoryPanels.tsx` 使用这些文案。
- `src/content/narrative/story-archive.ts` 维护获准显示的故事档案线索 ID 及其规则/世界/对话/文案引用；`src/main.tsx` 启动时校验引用，并把通过校验的 ID 投影传入档案 UI。
- 机械规则类型属于 `src/domain`，并由 `src/domain/expedition/validation.ts` 检查游戏内容定义。主题和内容的静态导入是目前的装载方式。

因此，当前代码已经是一个小型、类型化的运行时内容库。F-01 把现有故事档案 UI 作为第一个资料消费者：只读取代码已有的线索 ID 和玩家可见主题文案引用；Markdown 资料库仍是人工维护的编辑资料，没有被运行时解析。它也没有把候选路径、未实现世界或作者隐藏真相导入游戏。

## F-01 故事档案投影：已实现边界

投影位于 `src/content/narrative/story-archive.ts`。每条记录固定标记为 `approved` / `player-evidence`，并引用一个现有故事线索、对应主题文案，以及产生该线索的世界或对话。启动校验覆盖：重复记录、未知/漏登记线索、缺失文案、线索与世界来源不一致、对话没有实际授予对应线索。校验通过后才向 UI 提供 `{ clueId, copyId }` 白名单。

档案、主线任务和副本中的调查提示都从白名单取线索与文案；已发现状态仍由 Profile 决定是否显示证据正文，未发现线索只保留现有提示。投影不复制机械条件、奖励或真相，不写存档，因此没有 schema/content 版本变更。新增规则线索必须同步更新投影并通过引用检查。

自动测试只验证这一受限投影与现有代码引用，不校验 Markdown 交叉索引中的所有 `Q-*`、`W-*`、`PATH-*`、角色关系和来源 ID。它不是通用剧情图、模型上下文或候选素材导入器。

## 调研到的规范与适用范围

### 1. JSON Schema：校验外部 JSON 结构

JSON Schema Draft 2020-12 提供描述 JSON 结构与约束的通用词汇；结构校验能发现字段缺失、类型不符、枚举值非法等问题。[Draft 2020-12](https://json-schema.org/draft/2020-12) [Validation vocabulary](https://json-schema.org/draft/2020-12/json-schema-validation)

本项目当前内容由 TypeScript 静态导入，建议先用 TypeScript 类型、`satisfies` 和已有内容验证器表达契约，不急着添加 JSON Schema 依赖。如果将来希望非程序员直接编辑 JSON，再为该交换格式定义 JSON Schema。无论用哪种格式，结构校验都不能单独证明跨记录 ID 存在、关系方向正确、设定没有冲突；这些属于应用级语义检查。

### 2. W3C SKOS：借鉴分类与标签，不照搬整套语义网

SKOS 面向分类表、主题词表和概念体系，提供稳定概念标识、首选/替代标签以及层级或联想关系；其中 `related` 表示对称的非层级关联。[SKOS Primer](https://www.w3.org/TR/skos-primer/) [SKOS Reference](https://www.w3.org/TR/skos-reference/)

适合借用它来组织“环境、空间、异常、社会冲突、剧情功能”等多维分类，以及别名检索。不要把“关联”用于表达游戏因果。比如“极寒类副本”和“封闭设施类副本”可以是两个分类标签；“完成测绘项目后取得线索”必须用方向明确的 `produces` / `requires` 关系。

### 3. W3C PROV：记录来源、加工活动和版本责任

PROV 区分资料实体、产生或修改资料的活动、参与者/工具，并能记录派生和修订关系；它明确把来源描述作为一种元数据。[PROV Primer](https://www.w3.org/TR/prov-primer/)

本库不需要 RDF 数据库。借用最小来源链即可：`SRC/READ → 研究或改写活动 → 原创的 W/EP/EV/FACT`，同时记录版本、采用了什么启发、哪些细节没有照搬。这样能区分“作品原文事实”“我们从中观察到的手法”和“本作原创设定”。

## 关系分成三套词汇

不要把分类、剧情因果、来源沿革挤进单一的 `related` 字段。

| 用途       | 推荐关系                                                                                                                                   | 例子                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------- |
| 分类与检索 | `broader`、`narrower`、`related`、`alias`                                                                                                  | `极端环境` → `暴雪`；`封闭空间` 与 `交通设施` 可交叉归类       |
| 剧情与玩法 | `requires`、`produces`、`unlocks`、`opens`、`answers`、`raises`、`supports`、`contradicts`、`variant_of`、`implemented_as`、`presented_by` | 河岸项目产出测绘册；测绘册开放值守员复盘；玩家选择开放不同契约 |
| 来源与版本 | `informed_by`、`derived_from`、`revised_from`、`reviewed_by`                                                                               | 某原创世界受“密闭交通空间”手法启发；某版世界卡修订自上一版     |

每条边至少包含 `from`、`type`、`to`；有触发门槛时再记录 `when`，有取证要求时记录 `evidenceRef`。只允许登记过的类型，关系两端必须能解析到现存 ID。剧情边有方向；分类词汇只有符合 SKOS 含义时才使用标准层级/关联关系。

## 运行时投影的最小契约

只有对游戏呈现、组合器筛选或模型安全上下文确有用途的资料才进入投影。建议后续在 `src/content/narrative/` 建立单独模块，并用 TS 的判别联合类型约束：

```ts
type NarrativeLinkType =
  | 'requires'
  | 'produces'
  | 'unlocks'
  | 'opens'
  | 'presented_by'
  | 'enabled_by'
  | 'answers'
  | 'supports'
  | 'contradicts'
  | 'variant_of';

interface NarrativeRecord {
  readonly id: string;
  readonly kind:
    | 'world'
    | 'clue'
    | 'dialogue'
    | 'event-family'
    | 'question'
    | 'objective'
    | 'project'
    | 'contract'
    | 'theme-copy';
  readonly lifecycle: 'candidate' | 'approved' | 'retired';
  readonly visibility: 'player-evidence' | 'model-safe';
  readonly gameRefs: readonly {
    readonly kind:
      | 'world'
      | 'clue'
      | 'objective'
      | 'project'
      | 'event'
      | 'event-choice'
      | 'dialogue'
      | 'contract'
      | 'copy';
    readonly id: string;
  }[];
  readonly links: readonly {
    readonly type: NarrativeLinkType;
    readonly targetId: string;
  }[];
}
```

这是契约草图，不是现有类型或已实现功能。运行时投影原则：

- `id` 稳定且不随标题修改；所有交叉指向用 ID，不用标题或行号。
- `gameRefs` 只引用 `src/content` 和 `src/themes` 的既有 ID；它不复制规则条件、数值或展示全文。
- `visibility` 是投影的允许范围；`author-only` 真相只留在作者资料库，不复制进运行时投影。`player-evidence` 只表示玩家可见的证据，不等于证据背后的作者真相。`model-safe` 记录须单独审阅后才允许进入模型上下文。
- 投影里只保存模型或组合器需要的短摘要与合法引用；若需要事实摘要，应有明确的用途、可见性和来源记录，不能把未审核长篇草稿直接塞入运行时。
- 新叙事内容若写入存档，必须遵循当前存档版本迁移和损坏恢复约定。纯展示、临时突发文本则不应偷偷变成永久事实。

## 用现有“倒流的河”故事链作映射样例

以下 ID 都能在当前源码中找到，展示资料库关系如何指向游戏，而不是重新写一套机制：

```text
event-choice: river-bridge/repair-crossing
  unlocks → project: river-survey

project: river-survey
  requires → event-choice: river-bridge/repair-crossing
  produces → objective: forest-river-survey

objective: forest-river-survey
  produces → clue: forest-river-record

clue: forest-river-record
  opens → dialogue: keeper-river-review
  presented_by → theme-copy: forest-river-record

dialogue: keeper-river-review
  requires → clue: forest-river-record
  choice: follow-river-coordinate → clue: river-coordinate → unlocks → contract: ruins-observatory-contract
  choice: protect-evacuation-route → clue: relief-route → unlocks → contract: ruins-relief-contract
```

规则出处：`src/content/story.ts`、`src/content/expedition.ts`。玩家可见描述出处：`src/themes/story-copy.ts`。资料库问题只有在存在明确的剧情证据链时才连接到这些 ID；例如当前 `Q-03` 是多站列车的候选问题，不能为了图看起来完整而硬连到河流样例。正式可玩门槛仍以代码为准。这个示例不声称游戏已读取统一图；它说明未来投影或人工台账应如何回指当前真实内容。

## 静态检查和运行时边界

后续静态检查至少应覆盖：

1. 重复记录 ID、悬空目标 ID、未知关系类型、错误的 `gameRefs`。
2. 状态不一致：未评审内容不得标为可生成；退役 ID 不复用；“已实现”必须对应实际代码引用。
3. 玩家/模型上下文泄漏：模型安全视图不得包含 `author-only` 内容、未发现线索、未解锁选项或隐藏答案。
4. 事件实例结构有效：必须引用已批准的事件族、已知事实 ID 和固定响应 ID；不允许输出机械效果或永久线索定义。
5. 冲突和因果需要人工审阅；脚本可以发现断链，不能替代故事逻辑判断。

将来 LLM 只应在受限事件槽位内生成局部表现。代码先基于当前已存档状态筛选可见子图、事件族和选项白名单，生成后校验引用和结构；校验失败则展示固定文案。LLM 结果不得绕过 `GameRuntime.dispatch` / 远征运行时命令直接改状态。当前代码没有 LLM 调用端口，此段是未来约束。

## 后续落地顺序

1. 继续用 Markdown 维护研究、世界卡、主线事实和人工交叉索引；先统一稳定 ID 和关系词汇。
2. 选森林—河流—古城分支走一次从资料库到代码的完整追溯，核对已有实现 ID 与未解决问题。
3. **已完成：**明确首个消费者为现有故事档案 UI，建立线索白名单投影和来源/文案引用校验；不把整本 Markdown 转成 JSON，也不引入图数据库。
4. 下一世界合同经资料评审后，再判断需不需要更丰富的关系投影；若仍只服务 UI，继续使用 TypeScript 静态定义，不急于增加外部编辑格式。
5. 只有在组合器或模型上下文成为具体需求后，才扩展到事件族、可见性裁剪和更广的关系检查；涉及存档结构时另行设计 schema 迁移。

这样既能跨世界、跨角色和跨支线形成网状记录，也能让重复任务骨架与不同世界种子组合；副本数量不再受当前手写世界卡数量限制，同时每次组合仍受已审定事实与游戏合同约束。
