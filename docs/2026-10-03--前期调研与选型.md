# 桌面无限流增量游戏：前期调研与选型

调研日期：2026-10-03。本文是产品与技术建议，供后续迭代使用。游戏名、题材、数值、窗口尺寸和具体依赖版本尚未定稿。

证据范围：本篇最初调研核查官方游戏页面、开发者资料、官方源码与技术文档。当时尚无原型；后续已完成本地原型并扩展 v0.2，实际测试见 [验收记录](2026-10-03--工程基础搭建验收.md)。以下旧建议保留作为背景，不能把官方平台支持理解为本项目已经通过所有设备验收。手机同步仍未实现。

## 1. 用户已确认的方向

- 主要场景：Windows 电脑角落的小窗口，可置顶、随时收起，工作间隙偶尔操作。
- 后续场景：手机能接着玩同一存档。
- 起步循环：点击获得资源，购买/升级工具，工具提高产量或自动生产，逐渐解锁发展阶段。
- 无限流含义：进入不同世界或副本，每轮有任务和事件，部分成长带到下一轮。
- 搭建方式：从小规模开始，先确定产品与技术方向，再逐步增加内容。

建议定位为：**有跨轮成长的桌面增量放置经营游戏，逐步加入世界远征与规则挑战。** 它可以带有 Roguelite 要素，但首版无需实时战斗、走位或复杂地图。

“点击”提供起步和即时反馈；“自动化”让游戏适合摸鱼；“世界规则与选择”提供挑战；“跨轮解锁”让长期成长有方向。

对我们最有用的组合是：Cookie Clicker 的增长骨架、Rusty’s Retirement 的桌面形式、Microcivilization / Kittens Game 的规则挑战、Universal Paperclips / A Dark Room 的渐进揭示。

这些是机制研究参照，游戏的画面、名字、文本、剧情与具体内容需要原创设计。

## 3. 游戏的本质与特色建议

### 两层成长循环

```mermaid
flowchart LR
    A[进入一个世界] --> B[点击起步]
    B --> C[购买工具与自动生产]
    C --> D[升级并完成阶段目标]
    D --> C
    D --> E[本轮结算]
    E --> F[保留蓝图或解锁选择]
    F --> G[选择新世界与新规则]
    G --> A
```

本轮成长：资源、生产工具、建筑、局内升级和任务进度。

跨轮成长：新工具蓝图、可携带能力、世界解锁、收藏记录等。优先增加可选路线；大量永久倍率容易让后来世界失去挑战。

进入新世界前应清楚展示哪些东西重置、哪些保留、能获得什么。结算后等待玩家主动出发，避免自动开启下一轮让玩家错过选择。

### 无限流如何提供变化

无限流可以通过有限的世界模板、目标、规则修饰和事件组合，让玩家重复游玩。组合很多并不自动意味着一直有新鲜感，仍需持续验证选择是否不同。

示例只作为设计假设：

| 世界 | 规则变化 | 玩家需要改变的决策 |
| --- | --- | --- |
| 森林前哨 | 原料充足，自动加工设备效率低 | 先升级工具，还是先增加采集点 |
| 机械遗址 | 总供能有限，不同设备争用能源 | 选择哪些生产工具同时运行 |
| 风暴边境 | 扩张前需要储备，事件出现后待处理 | 选择更稳的生产路线，还是投入资源获取额外奖励 |

这些世界共享循环，但需要改变最划算的路线。第二个世界如果仍然只需要照抄第一轮的购买顺序，说明规则设计还没有产生足够差异。

初版从一个世界开始；验证完发展节奏后，再加第二个规则不同的世界。

### 挑战应适合工作间隙

- 阶段任务提供明确的小目标，少量路线选择形成资源取舍。
- 事件有预兆、可解释的成本和选择，出现后等待玩家回来处理。
- 首版离线主要补生产；事件不在后台产生不可挽回损失。
- 任务先按进度或主动操作推进，慎用必须准点在线的现实时间截止。
- 持续点击不宜长期成为最优策略；自动化应尽早让玩家能离开。
- 小场景逐渐增加设施或改变外观，让发展可见；鼠标点击、购买、解锁均有清晰反馈。

桌面建议有紧凑视图和展开视图：紧凑视图只显示小场景、主要资源、每秒产量、下个目标和待处理事件；升级列表与说明在展开后显示。默认静音，置顶由玩家控制。

### 题材尚未锁定

首选提案是“跨世界前哨站”：玩家携带一个小基地进入不同世界，建立生产、完成任务、带回技术或蓝图。这能自然容纳工具进化、多种环境和跨轮成长。

若更喜欢修仙，可以改成跨界修行据点；若更喜欢文明发展，可以改成漂流文明。它们会影响文案、美术和资源设定，因此应在原型前确定一个主题，不同时展开三条内容线。

## 4. 技术路线比较

以下平台能力来自官方文档；“适合程度”是结合目前需求作出的判断，并非性能排名。

| 路线 | 编写方式与工具 | 平台能力 | 对当前需求的取舍 |
| --- | --- | --- | --- |
| Web 技术 + Tauri | TypeScript；React 做界面；Vite 开发/构建；VS Code 编写；Tauri 提供桌面能力 | Web 核心用于浏览器，Tauri 封装桌面；手机可先做 PWA | **当前推荐**。资源、任务、升级以界面为主，便于数值迭代与手机重新排版；复杂场景能力按需增加 |
| Godot + GDScript | Godot 编辑器、场景/节点系统、GDScript | 官方支持桌面、手机和 Web | 当角色动画、地图、场景交互变成游戏核心时很有吸引力；Web 导出有额外约束，选它时优先 GDScript |
| Cocos Creator + TypeScript | Cocos 可视化编辑器与 TypeScript | 官方发布列表包含 Windows、Android、iOS、Web 和微信小游戏等 | 如果将来明确把微信小游戏等平台作为主渠道，可优先重新评估；当前小窗个人项目尚不需要这些渠道 |

依据：[React 组件与交互](https://react.dev/learn)、[Vite 开发指南](https://vite.dev/guide/)、[Tauri 简介](https://v2.tauri.app/start/)、[Godot 功能](https://godotengine.org/features/)、[Cocos 发布平台](https://docs.cocos.com/creator/3.8/manual/en/editor/publish/)。

Godot 免费开源，采用 MIT 许可；Godot 4 当前稳定文档说明 C# 项目不能导出 Web，Web 端依赖 WebAssembly / WebGL 2.0，并有后台暂停等限制。它仍然是可行路线，这些条件需要纳入选型。[Godot 许可](https://godotengine.org/license/)、[稳定版 Web 导出文档](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

### 推荐的具体分工

1. **TypeScript 规则核心**：点击收益、购买、自动产量、任务、事件、世界规则、离线补算和结算。与界面、操作系统和存储方式分离。
2. **React + CSS 界面**：小窗面板、资源、升级、任务与世界选择。Vite 用于本地开发与构建，不是游戏引擎。
3. **Tauri Windows 外壳**：窗口置顶、收起/托盘恢复和本地存档。
4. **配置化内容**：工具、任务、事件、世界规则保存为可校验的配置，后续扩展内容不必每次改整套逻辑。
5. **可选场景层**：早期小场景用图片和轻量动画即可。出现精灵、场景管理或大量互动需求时，再评估 Phaser；React 管界面，场景层管动画，二者共享同一规则状态。

Phaser 官方定位是面向桌面和手机浏览器的 2D Web 框架，支持 JavaScript / TypeScript；原生安装包需要额外封装。[Phaser 文档](https://docs.phaser.io/)

Windows 构建 Tauri 需要 Rust、Microsoft C++ Build Tools 和 WebView2；这意味着桌面打包仍有工具链成本。采用系统 WebView 不能推导本项目的内存或 CPU 已经很低，实际占用需要原型测试。[Tauri 开发前置条件](https://v2.tauri.app/start/prerequisites/)

本轮没有安装上述软件，也没有锁定依赖版本；开始实现时再核查本机环境并锁定适用稳定版本。

## 5. 手机、电脑与同步

### 三件事情需要分别实现

| 能力 | 建议方案 | 边界 |
| --- | --- | --- |
| 电脑角落运行 | Tauri 小窗口，支持置顶、隐藏与托盘恢复 | 属于 Windows 外壳功能 |
| 手机可玩 | 响应式界面，随后配置 PWA，可添加到主屏幕和缓存应用资源 | 安装支持因平台/浏览器而异；手机界面需要单独排版和测试 |
| 手机继续电脑进度 | 先统一存档格式与导入导出，后续账号云存档 | 跨平台运行不会自动共享本地数据 |

依据：[Tauri 窗口 API](https://v2.tauri.app/reference/javascript/api/namespacewindow/)、[系统托盘](https://v2.tauri.app/learn/system-tray/)、[PWA 安装指南](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)、[浏览器存储说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)。

手机 PWA 需要托管 Web 版本，通常通过 HTTPS 访问；首版桌面单机可离线运行，不依赖云服务。若以后需要原生 Android 安装包，可以增加对应工具链；Tauri 的 iOS 开发需要 macOS / Xcode，不能承诺仅靠当前 Windows 环境完成。[Tauri 移动端前置条件](https://v2.tauri.app/start/prerequisites/)

### 离线收益

隐藏网页的计时器会限速，后台动画可能暂停，Service Worker 也不是常驻进程。因此不能依赖“每秒定时加分”保证休眠、关闭、切后台后仍正确发展。[MDN 页面可见性](https://developer.mozilla.org/en-US/docs/Web/API/Page_Visibility_API)、[MDN 离线与后台运行](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation)

本项目建议：存档记录模拟已结算到的时间，恢复时补算新增时间段；补算后的资源与时间一起保存，避免重开反复领取。若期间触达任务、事件或生产规则变化，按规则分段推进。离线收益上限、事件等待策略和时钟异常处理要明确，不用强迫用户一直开着电脑。

### 本地存档与云存档路线

首版桌面用文件 / Tauri Store，Web 用 IndexedDB，通过存储适配层与规则核心连接。自动保存，重要购买和结算及时保存；保留最近备份，支持经校验的 JSON 导入导出。[Tauri Store](https://v2.tauri.app/plugin/store/)

存档建议记录：格式版本、内容版本、存档 ID、本轮 ID、随机状态、资源、工具、任务、待处理事件、永久成长和已模拟时间。浏览器本地存储可能被清理或淘汰，不能替代备份。[MDN 存储说明](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

后续云端候选：Supabase Auth + Postgres + 用户数据访问规则。账号能力和 RLS 可以控制身份与数据访问，但不会自动解决游戏存档冲突。选定服务前需要核查目标设备、实际网络、托管区域和费用。[Supabase Auth](https://supabase.com/docs/guides/auth)、[RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

云同步建议首先支持“设备接力”：电脑保存成功，手机加载该版本继续。每次上传带上一份云端修订号，服务端原子校验仍是该版本才写入；冲突时保存两份并让玩家选档，避免静默覆盖。[Postgres 条件更新](https://www.postgresql.org/docs/current/sql-update.html)

两个离线设备可能重复计算同一时段、完成同一任务，或各自购买不同工具。因此不能把金币、永久点数和离线收益直接相加；客户端保存时间更晚也不必然意味着存档正确。任意两端同时离线发展后自动无损融合，需要另一个更复杂的规则设计，不是首轮云同步的承诺。

## 6. 美术路线与软件

建议正式方向：**常规中文 UI + 小幅像素场景**。资源、数值和任务用清晰字体，场景通过建筑与设施变化表达成长。最初玩法原型可以先用矢量图标和占位图验证节奏。

| 方案 | 优点 | 制作成本 / 适用时机 |
| --- | --- | --- |
| 矢量图标、卡片与少量插图 | 排版灵活，快速验证，小窗与手机可共用图标 | 适合最初原型，需要后续补充成长的视觉表现 |
| 小像素场景 + 常规 UI | 有游戏感，设施升级容易体现，适合少量循环动画 | 推荐正式方向；要统一视角、像素密度、轮廓、配色和光源 |
| AI 辅助素材 | 适合探索世界气氛、背景与概念稿 | 同一建筑多等级和连续动画需要一致性检查、人工修整；不能省去素材规范 |

| 软件 / 素材来源 | 官方授权或免费状态 | 推荐用途 |
| --- | --- | --- |
| [Aseprite](https://www.aseprite.org/faq) | 官方发行版付费；源码可自行编译供自己使用；原创素材可商用 | 像素场景、设施和逐帧动画 |
| [LibreSprite](https://github.com/LibreSprite/LibreSprite) | 免费开源，GPLv2 | 零预算像素制作备选 |
| [Krita](https://krita.org/en/about/license/) | 免费开源；官网版免费，商店版可付费支持；原创作品可商用 | 背景、概念图、图片修整 |
| [Inkscape](https://inkscape.org/acerca-de/) | 免费开源，使用 SVG | 原型图标、世界标志和矢量装饰 |
| [Kenney](https://kenney.nl/support) | 官方资产页素材为 CC0，具体以素材页及随包许可为准 | 原型 UI、图标、场景及音效 |

可用的起步素材：[Kenney UI Pack](https://kenney.nl/assets/ui-pack)、[UI Pack – Pixel Adventure](https://kenney.nl/assets/ui-pack-pixel-adventure)，页面均标注 CC0。先采用一个风格系列，避免混搭；素材选择不应反过来锁死题材。

首版资产预算建议：1 个小场景、主设施约 3 个成长状态、约 8–12 个功能图标、一套面板/按钮/任务/事件样式，以及少量点击、购买、生产和完成反馈。通过一个样例确定素材规格，再扩大制作；这是工作量范围建议，不是已完成资产清单。

像素场景尽量整数倍缩放，中文 UI 独立按正常分辨率绘制；手机不要直接把整个桌面面板缩小，而应重排场景、升级与任务。[Godot 多分辨率文档](https://docs.godotengine.org/en/stable/tutorials/rendering/multiple_resolutions.html)

AI 适合做概念参考或少量背景；重复出现的设施、等级变化和动画仍需统一规范。保存可编辑源文件、素材来源、许可和生成/修改记录；实际使用前检查所用工具及素材的使用条件。

## 7. 从小规模开始的迭代路线

阶段是建议的推进顺序，没有承诺开发工期。

| 阶段 | 内容范围 | 需要验证的结果 |
| --- | --- | --- |
| M0：玩法验证 | 浏览器原型；1 种资源、点击、2 种自动工具、1 个阶段目标；占位美术 | 第一次自动化来得是否及时，购买选择是否清楚，短暂离开后是否还愿意回来 |
| M1：桌面可玩版 | Windows 小窗；1 个世界、约 3 种工具、少量升级、3 个阶段任务、1 个待处理选择事件；存档、离线补算、置顶/收起 | 关闭重开不丢进度，休眠补算不重复，事件不因离开造成失败，小窗文字可读且操作不干扰工作 |
| M2：无限流验证 | 第 2 个规则不同的世界、本轮结算、少量跨轮解锁、世界选择 | 同一购买顺序不再处处最优，跨轮成长提供新选择，重置过程清楚且有吸引力 |

| M4：持续内容 | 更多世界、规则组合、事件池和收藏 | 验证内容组合的可理解性和重玩价值，再扩充规模 |

无需一开始就建立联网多人、排行榜、付费系统或大规模后台。当前难点主要是增长节奏、低注意力体验、不同世界的策略差异和可靠存档。

## 8. 下一步要确定与验证的事项

已确定：桌面角落小窗口、多世界副本与部分跨轮成长、未来手机接续。

待确定：题材、主要操作对象、第一世界的任务/资源关系、离线收益规则。技术与美术推荐可在题材和首版玩法明确后定稿。

原型应检验三个产品假设。下面的时间仅是试验观察点，不是已确定的游戏数值：

1. 自动化能足够早地解放点击，同时还有值得回来的升级选择：开始约 5 分钟后能否放心离开，约 15 分钟回来时能否在 30 秒内看懂进展并作出一个有意义的选择？M0 的闭环只能验证起步，不能证明长期有趣。
2. 阶段任务和待处理事件能产生挑战，而不会不断打断工作：玩家能否说清两种事件处理方式的代价，并根据当前状态选择不同答案？等待期间暂停事件损失，避免事件变成无代价领奖按钮或持续惩罚。
3. 第二个世界的规则确实改变决策，跨轮能力不会迅速消除约束：同样的工具组合在两个世界中，购买顺序或资源分配是否变化？先验证一个小规则变体，再投入完整世界资产。

性能与设备验收留到实际原型：记录小窗活跃、收起、休眠恢复的 CPU/内存情况，验证 Windows 缩放、窗口置顶、存档恢复和手机触控。现在没有证据可以承诺具体占用、流畅度或存档同步可靠性。

建议下一步先写一页“第一世界玩法草案”：明确主题、点击对象、工具、3 个任务和一个事件，再制作 M0 原型。

费用方面，早期单机无需持续云服务；推荐美术工具有免费备选，Aseprite 官方发行版可按需要购买。后续 Web 托管、云存档、账号服务、应用分发与签名可能带来费用，应该按实际使用规模核查，而不是现在套用固定月费。首次原型也应优先利用已安装环境，不一次安装所有候选软件。
